# React rules

Project-specific React rules. Generic clean-code preferences live in `clean-code.md`. TypeScript specifics also live there.

## Components

- Function components only. No class components.
- One component per file. Filename matches the export: `DeckHeader.tsx` exports `DeckHeader`.
- Props are typed via a top-of-file `type Props = { ... }`. Don't `React.FC<Props>` — it adds nothing and used to add a forced `children` prop.
- React 19 forwards `ref` as a regular prop. Don't reach for `forwardRef` unless a third-party API genuinely requires it.
- Render functions are pure. Side effects go through hooks.

## Hooks

- `useEffect` synchronizes with external systems (subscriptions, the URL, a third-party widget). It is **not** for derived state — derived state goes in render or in `useMemo`.
- If you find yourself writing `useEffect(() => setX(deriveFromY(y)), [y])`, delete it and compute `x` in render.
- `useMemo` and `useCallback` are opt-in for measured wins, not reflexive. Most components do not need them.
- Custom hooks start with `use`, return either a value or a tuple, and live in `src/hooks/`. A custom hook that wraps one built-in hook with no extra logic is a smell.
- Don't read or write refs during render. Refs are an escape hatch; if a ref reaches across components, the data flow is wrong.

## State

- **Local first.** `useState` for everything that lives inside one component.
- **Cross-cutting client state** goes in Zustand stores under `src/stores/`, not in Context. Context is fine for genuinely tree-scoped values (theme, locale, current user) where re-render cost is low; Zustand is fine for everything else.
- **Server state** goes through TanStack Query. Never mirror server state into client state — it desynchronizes.
- No Redux. No MobX. No Recoil.

## Data fetching

- All HTTP goes through the generated `openapi-fetch` client in `src/api/client.ts`. Never raw `fetch` in components or hooks.
- Reads use `useQuery`, writes use `useMutation`. Mutation `onSuccess` invalidates the relevant query key prefix. See `api-client.md` for query-key conventions.
- Loading and error states are explicit at the call site. Don't render `data!` and hope.

## File and directory layout

```
src/
  main.tsx              # entry, wires QueryClientProvider, RouterProvider, I18nProvider
  api/
    client.ts           # configured openapi-fetch instance with auth middleware
    schema.d.ts         # generated by `pnpm api:generate`, do not edit
  components/           # reusable UI components (no route knowledge)
    DeckCard.tsx
    DeckCard.test.tsx
  features/             # feature folders combining components + hooks + stores
    deck-editor/
      DeckEditor.tsx
      useDeckEditor.ts
      deckEditorStore.ts
      DeckEditor.test.tsx
  hooks/                # cross-feature hooks
  i18n/                 # see i18n.md
  providers/            # ThemeProvider, AuthProvider, etc.
  routes/               # TanStack Router file-based routes
  stores/               # cross-feature Zustand stores
  styles/
    tokens.css          # CSS variables; the only place @apply chains live
```

A file under `features/<name>/` may not import from another `features/` folder. Cross-feature reuse goes through `components/`, `hooks/`, or `stores/`.

## Keys, lists, and identity

- Keys are stable IDs (`card.id`, `printing.uniqueId`). Array index is acceptable only when the list is provably static for the component's lifetime.
- Don't generate keys at render time (`key={Math.random()}`). It defeats reconciliation and is almost always a bug.

## Performance

- Profile before optimizing. The React DevTools profiler is the source of truth.
- Don't wrap everything in `memo()`. It costs a comparison on every render and rarely helps.
- For long lists (the card catalog, large deck imports), use `@tanstack/react-virtual`. Don't render 10,000 DOM nodes.
- Code-split at the route level via TanStack Router's lazy routes. Don't lazy-load below the route boundary unless profiling demands it.

## Suspense and error boundaries

- Suspense boundaries sit at route level by default.
- Error boundaries sit at route level by default. A component-level error boundary is justified when one route has multiple independent failure domains (e.g. the deck editor where a stats panel crashing should not take down the deck list).
- Boundary fallbacks use the same i18n keys as the rest of the UI — no hardcoded English fallback strings.

## Forms

- Controlled inputs by default. Reach for uncontrolled (`useRef`) only when a third-party widget owns the DOM.
- Form state lives in the component or in a `useReducer` for complex forms; do not spin up a form library (Formik, React Hook Form, etc.) unless a concrete form needs the features.
- Validation runs on submit and on blur for individual fields. Errors are announced via `aria-live` and tied to inputs via `aria-describedby` (see `accessibility.md`).
