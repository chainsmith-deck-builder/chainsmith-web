# Internationalization rules

Required reading before adding any user-visible string. The first commit of real UI in this repo wires up i18n; every commit after that maintains it. We do **not** add i18n later — adding i18n to an app that's accumulated hardcoded English is a months-long retrofit, and we are not paying that bill.

## Library

- **`react-i18next`** as the runtime.
- **`i18next-icu`** as the message-formatting plugin, so plurals and select-format use ICU MessageFormat instead of i18next's English-biased default.
- **`i18next-resources-for-ts`** to generate a typed key union from the English locale files at build time. `t('deck.editor.title')` is type-checked against the actual keys; misspellings are compile errors.
- **`i18next-browser-languagedetector`** for runtime detection (URL → `localStorage` → `navigator.language` → `en` fallback, in that order).

We do not use `react-intl`/FormatJS or LinguiJS. The decision is captured in the project plan and not revisited without a written justification.

## No hardcoded strings

Every user-visible string in this codebase goes through `t(...)`. That includes:

- JSX text (`<h1>{t('deck.editor.title')}</h1>`)
- Toasts and notifications
- Form errors (whether the message is generated client-side or pulled from the backend `ErrorCode` mapping)
- `aria-label`, `aria-description`, `title`, `placeholder` props
- `alt` attributes that aren't card-name-driven (card-name `alt` follows the card-data rule below)
- Document titles set via the router or a head manager

**Enforced by `eslint-plugin-i18next`'s `no-literal-string` rule**, configured to scan JSX text and the relevant prop set. The rule blocks merge; suppressing it requires a `// eslint-disable-next-line` with a comment explaining why and a follow-up issue link.

The escape valve for genuinely-not-user-visible strings (debug logs, dev-only assertions, internal route paths) is a `// i18next-extract-disable-next-line` directive. It is rare. If you find yourself reaching for it more than once a week, the rule is wrong, not the code — flag it.

## File layout

```
src/i18n/
  index.ts              # i18next bootstrap, ICU plugin, language detector wiring
  resources.ts          # generated by i18next-resources-for-ts (do not edit)
  locales/
    en/
      common.json       # shared chrome (buttons, dialogs, generic errors)
      deck.json         # deck builder
      catalog.json      # browse and search
      account.json      # auth, settings, profile
      errors.json       # typed against the backend ErrorCode union
```

- **One namespace per feature area.** New features add a new namespace rather than dumping into `common.json`. Namespaces ship as separate JSON files that `i18next` lazy-loads on demand, which keeps the initial bundle small.
- **`errors.json`** is special: its keys mirror the `ErrorCode` string union exported by the generated API client. New backend error codes light up as a TypeScript error in `errors.json` until you add a translation. See `api-client.md` for the wiring.

## Key naming

- **Dot-separated, lowercase, intent-revealing.** `deck.editor.empty_state.title`, not `deck.t1` and not `Deck Editor Empty State Title`.
- Keys never include the English copy literally — that defeats the abstraction. The whole point is that `deck.editor.save` can be "Save" today, "Sauvegarder" tomorrow, and the same key in code.
- Group by feature, then sub-feature, then leaf: `<namespace>.<area>.<element>.<part>`. `deck.editor.toolbar.add_card` is a fine key.
- When a key has variants (singular/plural, role-based), use ICU within one key, not multiple keys.

## ICU plurals and select

- Always express plurals with ICU:

  ```
  "deck.cards_in_deck": "{count, plural, one {# card} other {# cards}}"
  ```

  Never `count === 1 ? t('one_card') : t('many_cards')` in code. English-biased branching breaks for languages with non-English plural rules (Russian has three forms, Arabic has six).

- Use `select` for grammatical gender or role-based variants when needed:

  ```
  "deck.shared_by": "{role, select, owner {Shared by you} other {Shared by {name}}}"
  ```

- Dates and numbers go through ICU's `date` and `number` arguments, not raw `toLocaleString` calls in components.

## Locale routing

- Locale lives in a path prefix: `/en/decks/...`, `/fr/decks/...`. Deep-links carry locale, share-link recipients see the same locale as the sharer (which they can override).
- The router has a single `LocaleRoute` wrapper that reads the path segment, sets the i18next language, and re-renders.
- Detection on first load: URL > `localStorage` > `navigator.language` > `en`. The detector writes back to `localStorage` so a user who explicitly selects a language sticks with it.
- A user can switch language from the account menu. Switching updates the URL (and the browser history), not just the in-memory state.

## RTL readiness

We don't ship RTL locales yet. We pay the styling debt for RTL anyway, because flipping a fully-built app from LTR-only to bidi later is the same months-long retrofit we're avoiding for strings.

- **Logical CSS properties everywhere.** `margin-inline-start` over `margin-left`, `padding-block-end` over `padding-bottom`, `inset-inline-start` over `left`. See `css.md` for the Tailwind utility mapping.
- The `<html>` element gets a `dir` attribute matching the active locale (`dir="ltr"` for English, `dir="rtl"` for Arabic / Hebrew when those land).
- Any custom layout that uses arrow icons (back buttons, breadcrumbs) flips them in RTL via a `[dir="rtl"]` selector or a logical-property utility.
- We don't test RTL until we ship an RTL locale, but every PR that introduces physical CSS properties without a logical-property reason gets pushed back in review.

## Card data: names and rules text

The user's [decided rule](https://www.notion.so/352f137085018183ba6ccc050423bf9f), captured here:

- **UI chrome always translates.** Buttons, labels, errors, all of it.
- **Card names and rules text use upstream localized data when available, English otherwise.**
  - The backend's `Printing` (and possibly `Card`) types may eventually expose `localizedNames: Record<Locale, string>` and `localizedRulesText: Record<Locale, string>` maps, sourced from the `the-fab-cube/flesh-and-blood-cards` upstream dataset.
  - When those maps are present, the UI prefers the user's active locale and falls back to English on miss.
  - When they're absent (current state — the dataset doesn't ship localized data yet), all card content displays in English regardless of UI locale.
- **Card-name `alt` attributes** follow the same resolution: localized when available, English otherwise. The accessibility rule "every meaningful image has an `alt`" is unchanged.
- **Card-content components are the only UI in this codebase exempt from `no-literal-string`** for reading from the card-data API response — and only because the response itself is data, not strings the developer typed. The component still wraps the card text in a small renderer that respects the locale-resolution rule above.

A helper in `src/i18n/cardLocale.ts` does the resolution: `localizedCardName(card, locale)` returns the localized name when present, the English name otherwise. Components use this helper, not raw `card.name`.

## Extraction and drift

- **`pnpm i18n:extract`** walks the source for `t(...)` calls and `<Trans>` components, and updates `src/i18n/locales/en/*.json` in place. New keys are added with empty values; missing keys (still referenced in code but no longer in the JSON) are surfaced as warnings.
- The pre-commit hook reruns extraction and **fails** if the result diverges from what's committed. This is the same drift posture the backend uses for `openapi.json`.
- Translators (when we have any) work against the en JSON files via a translation management system. We do not auto-MT into the repo.

## Pseudo-locale (planned, not yet)

When we're ready to harden the i18n surface before launch, we add a build-time pseudo-locale (`en-XA`) generated from `en` with accented characters and 30% length inflation. A CI smoke build boots the app in `en-XA` and runs Playwright's overflow / clipping checks. Out of scope for the initial scaffold, but called out here so it's not lost.

## What to do when you're stuck

- **A backend `ErrorCode` is missing from `errors.json`?** Add the key to `errors.json` with an English message. The PR also bumps the i18n drift snapshot.
- **A copy change is needed but the key would be wrong?** Rename the key in the same PR. In `pre-launch` phase, key renames are free. In `production`, mark the old key deprecated, ship, and remove it later (same pattern as the backend's API field deprecation).
- **A new feature needs a new namespace?** Add it under `src/i18n/locales/en/<namespace>.json`, register it in `index.ts`, and you're done — the typed key generator picks it up on the next build.
- **You need a string in code that isn't user-visible?** It probably doesn't exist. Console errors developers see during dev are not user-visible. Internal route paths and feature-flag keys are not user-visible. If it's truly internal, suppress the lint rule with a comment.
